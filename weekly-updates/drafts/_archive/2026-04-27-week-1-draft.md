# Week 1: The unsexy week
*Week of April 27 – May 3, 2026*

I planned to deploy to Vercel and start using MasterMind nightly. Instead I spent two days rebuilding the plumbing under the floor so the rest of the house could keep being built.

---

## Where I was at the start of the week

Last week I closed Week 0 with a roadmap. Top of the list: **commit the Sprint 1 pile, push to GitHub, deploy to Vercel, start using the tool nightly with my family.** Right after that: Sprint 1.5 (Realtime cross-tab sync), then Sprint 2 (undo/redo).

I did almost none of that. The Vercel deploy didn't happen. The family still hasn't seen the app. What I did instead was a long, unglamorous infrastructure week — the kind of week where I spent two days writing code my user will never see and that my changelog buries under headings like "image storage migration" and "EditModal decomposition." This post is largely about why that was actually the right call, and the price I paid for not noticing the debt sooner.

## What I tried and dropped

**The Vercel deploy.** The very first thing on last week's "what's next." I never got there. The realtime work made obvious that base64 images would be unworkable over the wire, which forced the Storage migration, which dragged the App.jsx refactor along with it because the hooks needed clean extraction points. By Tuesday night the app worked better than ever and was still on `localhost:5173`. Cut, not on principle but on calendar — pushed to this coming week.

**The first Storage RLS policy.** I wrote a clean-looking SQL policy that inlined the campaign-ownership check directly in the bucket's RLS expression. Every upload then errored with `new row violates row-level security policy`. The cross-schema query from `storage.objects` to `public.campaigns` returns no rows even when the user actually owns the campaign — silently. Replaced with a `SECURITY DEFINER` helper function ([`public.user_owns_card_media_path`](../../supabase/migrations/002_card_media_bucket.sql)) that bypasses RLS on `public.campaigns` while still pinning the check to `auth.uid()`. This is now a documented pattern in CLAUDE.md so I don't rediscover it the hard way next time.

**The first attempt at the TextNode trash-icon delete.** My first instinct was to call `useReactFlow().setNodes((nds) => nds.filter(n => n.id !== id))` from inside the node component. The node visually disappeared, but on the very next re-render it was back. Turns out React Flow v11's `setNodes` doesn't emit `'remove'` change events when you filter from a controlled-mode `useNodesState` — it only emits `'reset'` for the kept nodes. App.jsx never learns the deletion happened, re-syncs from its still-stale state, the node returns. Workaround: a [`CanvasOpsContext`](../../src/lib/CanvasOpsContext.jsx) that exposes App's actual `onDeleteNode` to descendants. Ugly, necessary, well-commented for the next person.

**The first attempt at the TextNode toolbar buttons.** After fixing the delete-routing, the trash button still didn't fire after the second time I edited a text node. Native `pointerdown` reached the button, but React's synthetic `onClick` never saw it. Something between React Flow's NodeWrapper and React's root listener is calling `stopPropagation` in the bubble phase for selected nodes. I tried four different React-side patches before giving up and writing a small `NativeButton` wrapper that attaches native `pointerdown` + `click` listeners directly via a ref. Total time on this bug: about two hours, most of it spent not believing what I was seeing.

**The Realtime DELETE handler — first version.** I wrote the four `postgres_changes` listeners with a clean `campaign_id=eq.${campaignId}` filter. INSERT and UPDATE worked. DELETE silently dropped on the floor. Postgres' default `REPLICA IDENTITY` only puts the primary key in the DELETE broadcast, so the filter on `campaign_id` always rejects it. Fix was a one-line SQL change per table — `replica identity full` — but finding it took half an hour of staring at the Realtime devtools wondering if I was hallucinating.

Five different "the code looks right but does nothing" bugs this week. There is a pattern.

## What I learned

- **Infrastructure debt has a delivery date.** When I planned Week 1, I thought "Realtime → undo/redo → deploy." Realtime turned out to require image-storage to come first (for bandwidth reasons), which required `useImageUrl` and `Lightbox` and a migration tool, which exposed how brittle App.jsx had become. None of those were on the plan. This is the second time in two weeks the plan has been a polite fiction. I should start treating roadmap items as unblocked-by checklists, not promises.

- **"Decide now, build later" is a load-bearing pattern when you write in your own product.** ADR-0004 doesn't ship a feature. It locks the inline-mention syntax (`@[card-id|Display Name]`) so the prose I write in Strahd's notes today won't accidentally need migration when Sprint 4 finally implements the picker. Every word I type in the app between now and then is data I'll have to live with. The ADR cost me 45 minutes; not having one would have cost me a migration.

- **"Silently fails" is the worst error class.** Five examples this week: the Storage RLS policy returning zero rows, `setNodes((nds) => nds.filter(...))` not emitting remove events, React's synthetic event system swallowing clicks on selected RF nodes, Postgres `REPLICA IDENTITY DEFAULT` excluding non-PK columns from DELETE broadcasts, `el.focus()` being a no-op on a freshly-mounted contenteditable in Edge. None of them throw. None of them log. Each one cost me 20–60 minutes of "the code looks right." Going forward I'm going to be much faster to suspect "the platform is lying to me" instead of "I wrote the wrong code." That instinct shift alone would have saved hours this week.

- **Tests are permission to refactor, more than they are bug-catchers.** I wrote the ten EditModal tests *before* I started the 792 → 228 line decomposition. None of the tests caught a real bug. What they did was let me make changes confidently because I could re-run them after every move and prove the four happy-path flows still worked. That's the value, not a bug count. I should write tests at exactly the moments I'm about to do something risky.

- **The clearer the constraint I hand Claude, the cleaner the answer.** When I described the multi-tab DELETE bug as "the listener doesn't fire," nothing useful happened. When I rephrased it as "the broadcast `old` row only has the primary key — find me a way to make the row include `campaign_id`," Claude went straight to `REPLICA IDENTITY FULL`. Same pattern as last week's icon-flicker. The session where I struggled was the session where I described symptoms; the session where I shipped was the session where I described the constraint. I keep relearning this lesson. I should write it on a sticky note.

- **Ten lines of CHANGELOG is worth an hour of debugging next week.** I wrote three CHANGELOG entries this week, each long enough that they basically *are* mini post-mortems. When I bump into the same bug pattern in three months, the CHANGELOG entry is the artifact I'll find — not the commit message, not Claude's chat history.

## Where I am now

MasterMind syncs across tabs in real time. Images load fast and don't bloat the database. The EditModal is small, focused, and tested. The hover-and-select-state perf trap is gone — 100+ cards no longer re-render on every mousemove. App.jsx reads as orchestration over named hooks instead of a 700-line do-everything file. None of this is visible to a user; all of it makes the next thing cheaper to build.

What's still not true: I haven't deployed. The family still can't load the app from a URL. Custom node types still live in localStorage instead of the database. There's no undo/redo. There's no search. There's no AI. Roadmap items, all of them, all promised eventually.

Still on `localhost:5173`. Still solo. Still not embarrassed.
